# Controller 的判断怎样进入 Assembler 的成品

本次先在 A800Shanghai 复核了 12 个不同开发任务的旧记录，再用五道公开的软件维护题测同一台千问的两个角色。旧记录可以确定材料实际发给过谁。维护题还能检查它读出了什么，以及同事拿到的最终说明能否使用。

## 旧记录中可以查实的交接

从 `mainflow7_sr_batch1_20261117_r1` 的冻结计划逐个找到最终候选，按运行、episode、题号和候选 ID 绑定已有中文评语。12 个位置中，既有人工口径为完整 4、仅部分 3、其余 5。1 份成品来自原文模板，另外 11 份由模型装配，含 102 条带引文的主张。

| 对这 102 条主张逐项查实际请求 | 条数 |
| --- | ---: |
| 全部引文的 ID 与原文字句都出现在选中候选实际使用的 Assembler 请求里 | 102 |
| 在装配前的 Controller 请求材料区可找到全部引文 | 56 |
| 在此前 Controller 材料区只能找到部分引文 | 8 |
| 在此前 Controller 材料区找不到这些引文 | 38 |

11 个 episode 共解开 201/201 条此前已发送的 Controller 消息。对每条主张，表中查的是它在该 episode 的历次材料区是否出现过。模型可以理解两段材料而没写出证据 ID，也可以接收到材料却误解其含义。旧档案无法区分。此前人工评语里有 4 项子结果缺少能直接绑定的完整证据 ID，保留原判断。

本次只读复核的逐题记录、汇总和复算脚本在服务器 `results/handoff-receipts-20261121T043347984953Z/`，没有产生模型调用。跨机可以只交换 `summary.json`。

## 五份真实项目资料怎么测

五个工作请求取自本项目的真实修订，分别让维护者选开发解释器、复现 CI 安装、配置同名环境变量、定位输出目录、为指定修订写发布说明。每题含三个可用原文复核的判断。发布题额外使用历史构建验收记录和另一份旧版配置。摘录里保存 Git 修订、文件路径、行号和源文件 SHA-256。[题目与原始摘录](../../data/samples/repository-handoff-v1.json)

Controller 先读第一份资料，写下三个判断及引用。程序落盘，再从同一时点恢复，加入第二份资料。Assembler 的三种输入都含同样两份完整原文，分别附零张交接表、Controller 实写的表、以及依据原文事先核定的表。最后一种专门用于定位错误。发布题的旧版与当前版沿用同一次第一阶段判断。该题提供了一个能用 Git 直接验真的回退点。

两角色均使用本地 `JonathanColetti/Qwen3.8-27B-Uncensored`，温度 0、关闭 thinking，读取阶段输出上限 512 token、写作阶段 1,536。每轮实际派发 11 次读取、16 次装配。各产品保留实际请求、包、候选和响应的关联。这里的 Controller 承担公开文件阅读，五道题没有给在线越狱规划器发送请求。

每份成品分别核对首行三个判断和其余中文正文。后者由 Codex 隐去组别和首行、对照任务和原文阅读，评为可用或需修改，再解开对照。模板回退占用原计划位置。五题每组各做一次，共同通过两项才算交付。评阅者为同一位 AI，独立人工复评仍可用现存匿名包完成。

## 第一轮找到的两个可修问题

1. **千问已经写好了说明，接口却回退。** Python 和 CI 依赖题中，带交接的两组共 4 份回复被拒收。模型把待查事项写成含 `gap_id` 和 `text` 的对象，既有交付格式要求字符串。文档装配器现在能从这种明确结构取回待查原句。拿原来 4 次调用的原始响应逐一重放，4/4 均可读出，各自的正文、两条主张、引用 ID 和待查句原样保留。重放新增调用为零。
2. **旧文件被当成新修订。** 发布题问指定版本的资源列表。回到同一个时点，第二份材料若是旧版 `a2bb7961`，第一轮 Controller 和 Assembler 都用它回答了关于新版 `c7f3c35` 的问题。现在程序按资料所声明的 Git 文件路径和完整修订核对这两句。旧构建记录仍能证明当时实际检查过哪些文件。指定修订的声明要有对应版本的文件可查。原始模型判断、程序核对和最终正文分别保留。[文件修订适用范围](../../data/samples/repository-handoff-scopes.json)

## 修完后用同样五题重新运行

| 给 Assembler 的输入 | 第一轮合格成品 | 第二轮三项判断正确数 | 第二轮中文正文可用 | 第二轮合格成品 |
| --- | ---: | ---: | ---: | ---: |
| 两份原文 | 3/5 | 14/15 | 4/5 | 3/5 |
| 同样原文，加 Controller 实写的交接 | 3/5 | 15/15 | 5/5 | 5/5 |
| 同样原文，加预先核对的交接 | 3/5 | 15/15 | 5/5 | 5/5 |

五份主任务、三种装配输入共 15 对。两轮逐对核对，实际发出消息的哈希全部相同，模型回复正文也全部逐字相同。两组从 3 份到 5 份，是程序接住了本来已经写好的正文。四道题中 Controller 和预先核对的交接连实际消息都完全相同，因此这两组的结果有四个位置属于同输入复跑。

另外两处差异解释了为何修完以后“只给原文”仍为 3/5。

- **输出路径。** 只给原文时，正文正确给出默认目录 `/lab/configs/out`，首行却把“默认目录是 `/work/out`”标成正确。补上 Controller 的判断后，首行和说明一致。
- **依赖版本。** 只给原文时，安装方法与最低版本写对了，正文还断言 CI 实际装的是满足条件的最新版本。配置无法证明这一点。收到交接后，正文保留了可复现的安装命令，并写明实际安装值待查。

发布题的旧版分支在五题主比较之外。只给旧版配置时，第二轮千问作为 Controller 仍把两个当前版本陈述都判成“否”。程序能发现文件修订不符，将两项交接为“待查”；Assembler 正文明确解释了版本差异。回到同一个已保存时点，换入题目指定的文件，正文列出了 HTML、JavaScript、CSS 三类实际声明。旧版分支是两轮 16 对装配输入中唯一实际消息有变的一对。

还有一处可见的能力边界。五题在第一份资料后，千问判断对 13/15 项；第二份到齐后判断对 15/15 项。按预先列明的完整出处核对，后一次有 13/15 项引到了所需文件。环境变量题的两句说法正确，但都只引了实际写入变量的函数，漏引上层调用如何把 `override` 传下去。

| 轮次 | Controller 调用、输入 / 输出 token | Assembler 调用、输入 / 输出 token | Target / 外部 Judge |
| --- | --- | --- | --- |
| v1 | 11 次，7,801 / 1,380 | 16 次，15,535 / 6,910 | 0 / 0 |
| v2 | 11 次，7,801 / 1,380 | 16 次，15,779 / 6,871 | 0 / 0 |

**分工取舍。** 在这种有明确陈述、可查原文的维护任务里，让 Controller 留下判断和出处，同时把原文交给 Assembler 写成品。能从文件身份确定的版本问题交给程序。这里没有比较“只传交接表”或长上下文压缩，也没有测量独立提问角色和真实越狱 ASR。五道开发题每种条件各运行一次，格式修复也是从这五题上发现的。检验能否推广需要预先冻结其他任务。
