# Controller 要不要拆成两次调用

R22 的这次资料登记实验中，同一个本地模型在两种分工下都判断对了全部五个状态的缺项。把表达单独放到第二次调用，多派发了三次请求。两种分工都出现了知道该查什么、写出的问句却没有明确限定资料来源的情况。

## 现有越狱框架的调用链

批处理入口把所选分支的查询历史、在线候选反馈和当前预算交给 `LLMController.propose()`。规划输入还包括任务、活跃材料、缺项与组件状态。模板渲染后，动作类型与提议文本由同一次模型调用返回。R22 历史归档里的 22 条规划派发全部引用 `plan-evidence-v6.2`，冻结模板 SHA-256 前缀为 `e080123920a483d7`，已核对快照字节。当前普通演示配置引用 v6.1，历史实验身份以当时的回执为准。[批处理入口](../../src/framework/methods/independent.py) · [Controller 实现](../../src/framework/controller.py) · [R22 历史配置](../../configs/real-dev.mainflow8-sr-batch2.yaml)

## 本次如何比较

在 A800Shanghai 上用同一台 `JonathanColetti/Qwen3.8-27B-Uncensored` 核对两类资料，一类是材料里描述的资助条件，一类是论文的作者、刊名和发表年份。从 R22 三条带校验和的原文里截取连续片段，构造下表的五个可见状态。两个规划器在同一状态看到逐字相同的登记卡、已问字段和原文摘录。预期缺项单独保存在分析协议中。

| 状态 | 可见原文包含什么 | 还需索取什么 |
|---|---|---|
| `grant_window` | 年限 | 博士学位次序、向前计算的基准日 |
| `paper_title` | 刊名 | 发表年份 |
| `grant_complete` | 年限、哪次学位、截止基准 | 齐备，可以结束 |
| `paper_year` | 年份 | 期刊全名 |
| `paper_complete` | 刊名和年份 | 齐备，可以结束 |

A 一次返回决定、缺项、说明与问句。B 先返回决定、缺项、说明，决定继续时才由第二次调用措辞。第二次调用只收到条目名称和第一步实际写出的交接内容。两组使用相同的解码设置，温度 0，关闭 thinking。每组每状态最多输出 512 token，B 分配为 256 + 256。各状态交替使用 A→B 和 B→A 的运行顺序。模型调用归 Controller 的分析阶段记账，最终问句只写入实验目录。

“重问已知字段”按**已从可见摘录得到答案**判断。此前问过、但摘录还缺的字段可以继续问。为了自动读出实际索取的字段，登记协议要求在问句中用 `【字段名】` 标一次。程序独立检查问句中的标注、条目名称、资料范围用语，以及日期向前计算的方向。程序也单独保存规划器声明的缺项，两者可以逐题对照。[可执行实验](../../scripts/r22_controller_ab.py)

## 实测结果

运行目录为 `results/r22-controller-ab-b3d92fded0`。13 次本机调用全部返回 OK，正常停止。逐条核对了实际派发的消息哈希、参数以及 B 的交接边界。Target、Assembler 和独立 Judge 各 0 次调用。

| 读数 | A 一次完成 | B 规划后按需表达 |
|---|---:|---:|
| 缺项计划正确 | 5/5 | 5/5 |
| 材料齐备时结束 | 2/2 | 2/2 |
| 字段标注完全匹配（含两次结束） | 4/5，1 条缺标 | 4/5，1 条重标 |
| 严格表单通过（含两次结束） | 2/5，另有 1 条无法解析字段 | 2/5 |
| 实际问句写出预定资料范围词 | 0/3 | 0/3 |
| 模型派发次数 | 5 | 8 |
| 服务报告的输入 / 输出 token | 1,364 / 513 | 1,535 / 470 |
| 合计 token | 1,877 | 2,005 |
| 五个状态累计耗时（含编排） | 18.978 秒 | 17.888 秒 |

**逐句复核能解释为什么两个 2/5 不足以概括问句质量。** 六条实际问句都提到了所缺字段，阅读问题正文也没有发现要求再次提供已知字段的情况。形式及范围仍有具体差异。

- 只知道发表年份时，A 写的是「关于Clough & Stevenson的这篇短答案语料研究，请提供其发表的期刊全名。」索取项清楚，漏写了协议规定的括号。B 给刊名加了括号，但交接说明里的「短答案语料研究」到了问句变成了泛称「条目」。
- 只知道资助年限时，两组都保留了「从该日向前计算」。B 在索取字段和解释方向时各标了一次同一个 `【计时基准日】`，触发了重复标注。两组都没有再次索取年限。
- 六条问句都点明了条目身份，也都没有明确说「按这份材料的记载」。对于资助条款，这会影响对方是复述材料里的说法，还是回答现实中的政策。自动分数衡量预先规定的表单和措辞，以上逐句阅读补充解释了发生在哪一层。

这五个状态取自同一包的两份短资料。B 合计多用 128 token，约 6.8%，本次累计耗时略短。一轮交替顺序的测量无法区分服务负载和缓存对耗时的贡献。当前以一次调用作为这类资料登记的基线更省调用。长历史中的表现、自由表达的语义效果和最终越狱 ASR 需要各自的实验。

## 复核与重跑

服务器仓库根目录下，下面的命令只读既有逐题结果，会列出未标字段、重复标注和原问句，也会重算两组成本。已经落盘的判定保留原口径。

```bash
~/sci-deepseek/.venv/bin/python scripts/r22_controller_ab.py --report results/r22-controller-ab-b3d92fded0
```

需要独立重跑时，执行 `~/sci-deepseek/.venv/bin/python scripts/r22_controller_ab.py`。程序创建新目录，派发前保存协议，每个状态的每组产物分别落盘。首次实验用的脚本提交为 `d15a06f`。后续增加的只读解释会显示缺标原因。命令退出码区分调用故障与已测得的表单不合格。
