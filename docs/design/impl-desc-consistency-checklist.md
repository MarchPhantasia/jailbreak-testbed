# 实现-描述一致性审查清单（2026-11-26 立）

**性质**：每轮含代码改动的交付，提交前与提交后各跑一次；review 任何历史轮次时也按此清单核对。
**判定**：任何一条"描述说了而代码没做"或"代码做了而描述没说"的差异，要么修代码、要么修描述，
当轮写进 changelog，不允许带差异进入下一轮。

## A. 逐条主张核对（提交级）

1. **主张→锚点**：交付文档/changelog/提交信息里每一条"做了 X"，在代码里指出唯一锚点
   （文件+行为）；grep 不到锚点的主张当场降级为"未做"。
2. **量词核对**：描述里的"所有/每/全部/仅/一次"与实现的作用域逐个比对
   （例：说"所有 ask 指令加约束"，就枚举全部 ask 指令构造点验证，不能只看两处）。
3. **参数核对**：描述里的阈值/次数/条件（"≥1 条实质回复""前 40 字符含数字"）与代码字面量比对。
4. **测试主张核对**：声称的测试数量、断言内容、测试名，与测试文件实际内容比对；
   测试没跑过的（收集失败/静默跳过）不算数，必须显式跑过并看到 pass 行。

## B. 行为级抽查（运行级）

5. **烟测产物核对**：描述的运行行为（"13 target""零缺失叙述"）能在 events/candidates
   里指出对应字段；用真实产物复验，不用记忆。
6. **不变量复跑**：全套 pytest + precheck 在提交前跑过并记录数字；描述里的数字与
   实际输出一致。

## C. 历史回溯（review 级）

7. **口径漂移**：本轮描述与上一轮对同一机制的描述若有不同（阈值变了、作用域变了），
   必须在 changelog 写明"从 X 改为 Y，原因是 Z"，不能静默改口径。
8. **未做项清点**：方案里提了但本轮没做的（如某杠杆的子项），显式列为未做项，
   不混在"已完成"的表述里。

## D. 本清单自身的维护

- 清单更新需要理由记录；新增条目带日期。
- 审查结果以"差异列表"形式写进当轮 changelog（无差异也要写"一致性审查通过"）。
