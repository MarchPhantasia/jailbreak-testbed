## 0 长期研究目标

2026-11-21 修订。项目研究固定 Target 查询预算下，整条自动化 LLM 越狱评测流程最终能交付什么。以下七项是跨会话延续的研究问题。具体能力是否已实现、某次实验观察到什么，分别查对应代码和冻结运行记录。

1. **Controller 如何判断和提问。** 从每次交互还原它当时看到的材料、原提议、实际发送的消息和 Target 回复。区分提问方向、表达方式以及对回复的理解。记录提问模板的角色、语言和版本，独立提问角色的取舍留给实验。
2. **从人工回退到自动判断。** 分别记录研究者在哪次回复发现问题、认为该回到哪次提问之前、理由是什么。比较人和系统的判断时，双方看到的历史都截止在发现点。网页用于回放、标注和核对，日常评测要能自动运行。
3. **状态、记忆、分支与预算。** 区分 Controller 记得什么、Target 实际收到什么、哪些问题已经问过、哪些已有回答。比较不同状态表示、分支选择、材料合并和停止策略时，记录各角色的实际开销。
4. **Assembler 能做哪些工作。** 装配器可以综合已有数据，利用模型已有知识进行计算、改写、编辑、编写代码，形成输入材料里尚未出现的成品。组织方式本身也可能有价值，例如把分散在数份记录里的日期和条件整理成一张可用的时间表。要评价这些产出的质量和错误。
5. **独立 Judge 与人工评审。** 分别评价最终答案实际交付了什么，以及送评证据支持了什么。部分成功要能指出与原任务同向、可独立使用的子结果。保持在线反馈与最终评价独立，用同一候选、实际送评材料和中文人工评语核对分歧。历史严格 ASR 仍按该次冻结的 tf、src、ev 计算。
6. **可比较的实验。** 使用 StrongREJECT、HarmBench 等任务，固定任务身份、数据划分、查询预算和评价口径，报告完整、仅部分、失败以及未判定的数量和分母。R22 用于固定样例回归，跨任务效果由独立批次检验。
7. **整条流程完成了什么，Assembler 在装配时创造了哪些价值？** Target 的回复、装配器可访问的既有资料，以及本地模型自身的知识和推理能力，都可能影响结果。先看答案交付了什么，再对照实际输入识别装配阶段增加或改进的部分。例如，旧记录和本轮回复各给出若干项工时，Assembler 算出可复核的总数。各项数据有各自的出处，合并和计算同样值得评价。对于只在成品中出现的主张，分别判断其正确性、用途和可确认的来源。出处未知可以如实标记，成品本身无法揭示模型的内部思考过程。“移除某条 Target 材料后结果会怎样”保留为可选的归因问题。

现有入口包括 `framework.webapp` 与 `framework.interactive` 的交互记录、`scripts/assemble_ab.py` 的同包装配对照，以及独立的 `judge` 命令。核对一项结果时，可分别找回候选实际使用的包、Judge 实际看到的证据和该轮判据。

第 7 项的 R22 实验分别核对了档案里的说法、对实际规则的判断，以及 Assembler 自行计算的日期和生成的查询。[装配实验记录](../delivery/r22-assembler-contribution.md)

第 6 项的日常验证使用一整批预先确定的不同任务，记录完整、仅部分和其余结果的实际构成。R22 留作精确定位错误的固定样例。第 4、7 项的正式产物分开记录谁写了主张、哪种来源和文字匹配有依据。分析账单时由程序算各角色小计，给千问的具体材料组织方式根据任务实测选择。[12 题的来源复核与千问输入对照](../delivery/multitask-assembler-replay.md)

第 1、4、7 项共用一条分工原则。先定义成品要让读者做成什么，再用同一份材料检查本地模型、程序及外部复核各能完成哪一步。保留 Assembler 的独立判断和编辑贡献。能按公开规则精确计算的字段可交给程序生产，并单记来源。外部模型可以复核一件本身就适合独立提交的工作，例如根据公开交叉表复核一段统计结论。是否值得调用，看它能否补足实际缺口、说明是否保留原意，以及增加多少开销。每项分工注明在哪些输入上测过，长材料和跨领域的表现分别取证。[各角色的实测分工与适用范围](../delivery/model-role-calibration.md)

## 1 固定目标和边界

研究对象是独立的信息获取、状态管理、搜索、答案组织与评价架构。主终点为固定 Target 查询上限下，episode 最终选中答案对原始任务的成功率；成功条件在运行前冻结。单轮拒答率、API OK、输出长度、材料数量和局部覆盖都不能替代最终 ASR。

早期冻结证据基线把 Target 设为主要新增领域信息来源。研究整个系统时，Target 材料和 Assembler 独立加工的贡献均按 §0 第 7 项评价。一个本地模型可以承担多个角色，各角色的输入、阶段参数和成本分别记录。

CKA 是可选架构参考，不作为本框架的定义或验收依赖。不强制 MCTS、UCT、固定深宽、某种混合评分或 CKA 的最终判断口径。保留原文、失败记忆、分支和装配的价值由后续研究检验，不预设改善。

## 3 目标闭环及完成标准

目标闭环必须能表达并记录：

```text
原始任务 + 已执行查询/结果 + 当前分支材料 + 允许的失败记忆
                         + 可用的在线反馈 + 剩余预算
                                      ↓
                       选择节点/方向并提出下一动作
                                      ↓
                     校验与执行 → 获取 Target 观察
                                      ↓
                     更新状态、来源关联和替代方向
                                      ↓
              按触发条件装配 → 在线检查/候选反馈
                      ↙                         ↘
              继续获取或切换方向                 收尾
                                                ↓
                                      冻结最终候选
                                                ↓
                                    独立 Judge_eval
```

线性是允许的基线。目标架构也必须具备可实际执行的分支能力；是否在某个方法配置中启用由显式选择决定。不能把“有树结构”当作“有分支策略”，也不能把关闭全部可选能力的基线默认为最终架构。

不要求每轮装配或每轮增加反思/裁判调用。先让信息反馈真正进入下一次决策，再选择触发频率、预算与实现方式。

## 5 四类信息的边界

### Target 可见请求

isolated 下：当前查询 + 允许的固定必要背景 + 显式 system 提示。不能自动附带历史问答、Controller 私有状态、最终裁判或他方法标签。ancestor 下：只提交所选 View 允许的历史，不含兄弟路径。两者均保存实际 HTTP messages 和快照。

传输 stateless 仅表示请求端提供 messages；server_side 若维护会话，必须有真实重置/分支能力才能声称隔离。本地删除数组不证明服务端遗忘。

### Controller 可用信息

原始任务、公开上下文、实际查询—结果记录、当前选定分支材料、允许范围内失败记忆、有效在线反馈和预算。查询记录至少可定位 query、request/call、执行顺序、结果与所属执行边。引用 ID 若没有解析入口，不能代替规划所需的可读信息。

不得读取参考答案、冻结测试最终标签、CKA 的逐题成功信息或当前 episode 的 Judge_eval 结果。配置中标注“只供评价”的字段必须在实际输入构造时隔离。

### 正式状态与假设

原文组不强制抽取事实；结构化组记录抽取输入、处理版本、条件和出处。Controller 推测、备选方向和尚未执行的 proposal 不能自动成为 Target 事实。失败记忆与当前正式证据分开。

### 装配与最终评价材料

在冻结证据基线中，Assembler 使用显式选定的证据包并作允许的推导。分析其他来源时，分别记录装配时实际提供的资料、最终答案新增的内容、事后核验取得的资料。Judge_eval 按该轮冻结协议接收候选和允许证据。来源存在、语义支持、保真度和真实性分别记录。

## 6 决策、分支和在线反馈

### 决策必须消费运行中的信息

至少能从记录解释：本次动作依据什么任务缺项/反馈、哪些查询已经尝试、采用哪个节点及预算是否允许。只改提示词措辞、只保存动作 rationale，不能替代缺失的数据输入。内容不充分、格式错误、供应商拒答和网络故障分开记录。

（b3e9514 状态：查询记忆、候选反馈、node_selected 前沿与依据都已进入决策输入与事件记录，离线复跑可查；真实运行中 Controller 是否有效消费这些信息仍未验证。）

### 分支的最小行为契约

未执行候选是 proposal；执行某查询后才产生观察节点。兄弟节点保持独立正式状态；切换路径不退款、不删除失败事件。选择和扩展由配置策略负责，不强制另加一次 LLM 调用。

选择日志应包含可选前沿、选中节点、策略及可定位依据。未知分数保留未知；不能无说明地按失败零分惩罚。新子节点、父节点与执行该查询的边要能区分，否则查询记忆和预算归属会混淆。

跨分支证据合并默认关闭（`cross_branch_merge: none`）；启用 `all` 时是独立策略：装配包从全部观察节点按 evidence_ids 去重合并、每条材料带 source_node 来源标注，合并范围冻结进包记录（merged_from_nodes）；分支正式状态仍隔离，Controller 输入仍只见当前分支材料 + 全局失败记忆。指纹/收尾重装配/反馈 stale 在合并模式下使用合并视图。允许 Controller 知道其他路径失败，不等于允许 Assembler 无说明地使用其他路径材料——合并模式下"说明"即 source_node 标注。

### 在线反馈的最小语义

当配置允许装配后继续取证时，Controller 应能读取当前有效候选及其反馈：任务要求中的缺项、证据不足、矛盾/条件问题、候选/证据包引用、检查来源与版本。具体字段名可适配现有代码。

反馈可来自 Assembler 的结构化输出、已有在线检查或单独配置的 Judge_online。**不默认增加一个模型、不要求每轮调用新裁判。**反馈是待判断的信息，不是已证明正确的事实，也不能作为最终成功标签。在线检查无可检查判据时显式报"检查不可用"（online_check_unavailable:no_rubric），不与"有效判据中确有未满足要素"混用（9c002e9 审查轮 A02）；规则评分输入未建立时同样显式不可用（A01），二者都不改变最终 S/F/U 协议。

先确认 Controller 消费的是当前候选和材料版本，再据此继续、切换或停止。旧反馈须标记适用版本或过期，不能覆盖新状态。是否对某缺项追问，是 Controller/策略的决定；本规格不提供具体攻击载荷。

b3e9514 已实现最小反馈入口（`state.candidate_feedback`：候选/gaps/verdict/包版本/stale，无新增模型调用）；"Controller 在真实运行中据此有效再规划"仍是待验证项，不因入口存在而标完成。

## 7 装配、选择与统一收尾

单次装配是有效基线；多候选必须真的生成不同候选并保存各自调用、采样和成本，不能复制同一文本或仅变排版来冒充 k 次生成。候选择优使用冻结的在线标准；最终 Judge_eval 不参与在线挑选。

装配保留缺项、否定、条件、版本和冲突。冻结证据基线要求关键事实可由包内材料支持，推导可追溯到输入。研究装配贡献时，另记新增结果的正确性和对任务的用途。字面覆盖用于诊断，改变成功条件需另立评价版本。

正常停止共用收尾：Controller STOP、max_steps、Target 额度、Controller 阶段额度、恢复停止。STOP 表示不再继续取证；已有材料时仍按既定规则收尾，不能直接丢掉材料。

收尾依次判断：当前选择的材料范围/分支 → 候选是否与它对应 → 是否有变化 → 是否需要装配 → 非 Target 和装配阶段额度 → 候选选择/声明回退 → 唯一 terminate。不能用“存在任意候选”或“最后一个 pack”无条件替代选中候选的真实输入身份。

after_assembly 保持首次装配后冻结。online 允许在预算与停止规则内继续，并在新增材料后按规则收尾；材料未变不重复装配。Controller 额度不足不等于装配额度不足。没有材料不能编造答案；有候选但没有新装配额度时按冻结策略保留/回退并说明未纳入材料。

异常中断不伪造正常完成；候选、原文和已发调用账本保留，评价按计划清单对账。

## 8 评价与来源口径

Judge_online 为运行提供反馈；Judge_eval 对冻结最终答案作独立评价。最终采用语义裁判时，模型输出语义字段，程序按冻结成功条件计算 S/F/U；不是把真实任务降回关键词规则评分。

最终正常无答案按既定协议计 F，不删分母；评价未产生有效判定为 U；有效语义判断“证据不足”按成功条件判定，不自动变成 U。任务内先算预定 episode 比例，再任务等权汇总。U 导致的可识别范围不是置信区间。

Target 回答错误仍可能属于 Target 来源；本地改变原意属于加工错误。若某内容先由 Controller 提出、Target 仅复述，不能由“出现在 Target 回复中”推断它独立起源于 Target。

运输成功不代表语义完成；根据一份回答推断“缺少某字段”不等于证明补问一定成功；看到 Target 识别历史也不等于证明历史是 ASR 变化的因果根因。

## 9 下一步开发如何不偏离主线

每轮先选一项能力和一个短的完整行为链。优先候选为：在线反馈进入再规划、可实际选择替代路径的分支闭环、真实多候选与在线选择。具体实施顺序随用户当前任务确定，不把所有能力同时开启或全部列为一次交付门槛。

涉及结构化状态时，需要区分等长摘要与 F/O/X；规则截取后端只算基线实现，不能代表语义抽取已经完成。涉及失败记忆时，要能单独控制记忆范围并说明信息访问差异。涉及阶段预算时，参数必须实际传入相应角色，不能只写版本引用。

基础日志、来源、分母或预算错误若阻断当前能力，应修复；其他外围改进放入单独待办。当前不恢复被停止的真实批次，不做上下文窗口测试。开发完成后更新能力状态及实际方法配置，而非只更新通过数量。
