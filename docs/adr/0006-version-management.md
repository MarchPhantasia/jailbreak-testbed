# ADR-0006：版本管理由单一维护者负责，规格版本与代码版本分离

- 状态：已接受
- 日期：2026-11-11

## 背景

仓库当前只有规格，后续会并行出现"本地开发"与"远端评审"两条线。若不做约定，会出现三个问题：规格改动无法追溯、代码与规格版本混淆、评审看到的与开发手里的不一致。

## 决定

1. **单一维护者负责合并与推送**。开发可在本地进行，但进入 `main` 的动作由维护者执行。
2. **规格版本与代码版本分离**：tag 形如 `spec-v1.1`（规格）、`v0.1.0`（代码）。两者不互推。
3. **分支模型**：`main` 随时可读；工作分支用 `spec/`、`docs/`、`feat/`、`fix/` 前缀。
4. **每次进入 `main` 前必须过 `scripts/precheck.sh`**：JSON 可解析、rubric 不变量、文档内链、体积与密钥特征、工作区状态。本地以 pre-commit 钩子执行，远端以 CI 冗余执行。
5. **规格变更必须同时更新 `CHANGELOG.md`**，并在 `Unreleased` 段落里写清"改的是哪条契约"。

## 理由

- 规格是这一阶段唯一的产物，版本混乱的代价全部落在实验解释上。
- 单一维护者合并，可以保证"评审看到的就是最新的、且都过了检查"。
- 自动检查把"文档写坏"的成本压到提交时，而不是评审时。

## 后果

- 开发侧的提交需要经过一次转手；换来的是主线始终处于可评审状态。
- precheck 会拦住合法的临时改动（例如故意留一个坏链做演示），此时应改流程而不是绕过钩子。

## 被否决的替代方案

1. **完全放开推送权限**：多人直接推 `main`，评审时无法判断哪一版是基线。
2. **用一个版本号兼管规格与代码**：规格改一次就要发一次代码版本，反之亦然，语义会迅速失真。
3. **只在 CI 做检查**：反馈太晚，且本地提交历史会留下坏状态。
