# 规划输入、装配输入与证据复核

Controller 的模板路径会收到任务、当前分支已问记录、活跃材料、候选反馈和预算。同一次规划调用可以同时产出动作和提议文本。Assembler 从所选冻结包取得材料、组件、缺项和引用 ID。Judge 使用自己当次评价的送评范围。三处即使出现同一个证据 ID，实际附带的文字也可能不同。

## 在已有运行里查看输入

打开网页的「回放」，选择运行和任务，展开「规划和装配实际发出了多少内容？」。命令行也可以读取同一份报告。以下目录取自固定样例 R22 的清单。

```bash
python -m framework.cli audit --episode-dir results/mainflow8_sr_batch2_20261117_r1/episodes/ep_49f441c969 --context
```

这些数值来自 episode 事件中的原始请求。已有中文译文只用于工作台展示。

| 读数 | 怎样解释 |
|---|---|
| 派发、缓存 | 每条 `request_sent` 计一次派发。缓存命中单列。派发也包括服务超时的请求。 |
| 消息字符数 | 对记录中的各条文本消息求 Unicode 字符数之和，不含协议封装。消息缺失或格式不支持时为 `null`。 |
| 输入 token、耗时 | 从同一 episode 内能唯一关联到该次派发的结算记录读取。缺失为 `null`，账本明确给出的 0 保留。阶段合计和峰值同时报告有读数的调用数。逐次 `wall_ms` 是该调用耗时。 |
| 模板和输入 JSON | 事件里的模板哈希与冻结快照匹配、记录中的用户消息符合该模板时，分别测量固定文本与动态 JSON 的字符数。旧渲染、缺快照或无法核对时仍报告消息总长度。 |
| 材料正文、重复正文 | 每份材料取 `value`（缺失时取 `text`）求字符数。“重复正文”只比较不同材料条目。同一条目内同时保存的 `value` 与 `text` 都计入动态 JSON 长度。 |
| 当前分支已问记录 | 取自该次 Controller 输入中的 `state.queries`。整个 episode 的派发时间线另在工作台展示。 |

固定样例 R22 的历史回放已有每次派发的字符数。按清单核对运行目录、episode 和任务身份后，从 `request` 记录得到以下读数。

| 角色 | 有长度记录 / 派发 | 首次输入字符数 | 单次峰值 | 末次输入字符数 |
|---|---:|---:|---:|---:|
| Controller | 22 / 22 | 6,272 | 27,314 | 24,380 |
| Assembler | 2 / 2 | 149,158 | 149,158 | 149,158 |

在这两个角色中，装配的单次输入最长，规划的派发次数更多。两次装配长度相等，核对消息原文才能确认内容是否相同。判断长度是否引发质量变化还需要固定材料的对照。

## 自动运行 R22 阅读对照

在已有 R22 档案和本地 Assembler 服务的服务器上，从仓库根目录运行下面一条命令。

```bash
~/sci-deepseek/.venv/bin/python scripts/r22_reading_ab.py
```

A 使用原包全部材料字段。B 只把每个条目里与 `value` 完全相同的 `text` 替换成同字段引用。程序先还原 B 并与原材料逐项比较，也核对包的两种哈希、原文校验和及行号与证据 ID 的顺序。两组使用相同的问题、材料顺序、模型和参数。两组共用专门的原文阅读说明，因此 A 的总字符数会与历史装配请求不同。

同一台装配模型各读一次材料，回答三个已有原文可逐字核对的问题，涉及材料声称的资格年限、学位条件和语料研究出处。判分程序分别核对值、引文是否保留要求的条件、所报证据 ID 能否定位到预先登记的支持行。允许的等价答案与已确认的出处在派发前冻结。其他位置的逐字命中也记录在 `matching_line_ids` 中，可复核。结果衡量材料阅读与定位，条款的客观真实性另行判断。

输出在一个新的 `results/r22-reading-ab-*/` 目录。两臂分别有自己的结算记录及 `arm-A.json`、`arm-B.json`，汇总见 `summary.json`。未完成的核对项保留在三个计划问题的分母里。温度为 0、每臂最多 768 个输出 token。A→B 单次运行的耗时可能受服务端前缀缓存与负载影响。

## 从候选回到原文

回放页打开「查看最终候选」，或在「对照」页选择两份候选。展开一条主张下的回复事件，再展开引用，可看到该条原文、字符起止位置及各次 Judge 的送评回执。字符区间为左闭右开。兼容旧记录时，缺校验和的原文附提示。同一 ID 的原文或来源位置互相冲突时，页面显示冲突。

R22 的引用复核解释了为什么这些层次值得分开。表达同一句主张时，引到一段前言和引到支持它的原句，读者的复核成本不同。把一整份材料列为引用会提高包含支持句的机会，同时也会带入无关行。核对时可直接打开对应的行，判断限定条件、版本和否定是否保留。[R22 引用复核记录](delivery/r22-citation-closeout.md)

## 如何判断拆角色与缩短上下文是否值得

规划和文字表达可以共用同一次模型调用。独立调用会再读一份输入，还会产生交接时遗漏条件的可能。比较两种组织方式时，应固定工作目标和可见材料，检查输出是否保留同一意图、约束与来源，同时比较全部本地调用的 token 和耗时。一次调用的输入变短，只能说明该次调用的长度发生了变化。

对装配而言，完整留存的档案、实际送入模型的材料、最终所列引用是三个可单独核对的对象。评估压缩效果时，尤其值得看需要同时读取两段原文的例子，例如旧版给出一个数值而新版把它标为「待确认」。仅核对数值能否复述，会漏掉这个限定。以现有冻结材料做复核可以复用既有人工意见。归档长度本身无法给出某个 27B 模型的最佳窗口或质量结论。
